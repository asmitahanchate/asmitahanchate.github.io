What RAG is, and where I'd already built it

Asmita Hanchate· Nov 20, 2026· 9 min read· RAG

I learned something properly today, and I want to write it down while it's fresh. Twice this year an agent I worked on gave answers that sounded confident but weren't true. In both cases the model itself was fine. The problem was simpler: the model never saw the right information. So today I took a step back, went over the basics the right way, and then built a small project to test what I learned. Here's what I found.

The basics, in plain words

Language models have three recurring problems:

  • They can make things up. This is hallucination.
  • They can only read so much at once. That limit is the context window.
  • They don't know your private data. They only know what they were trained on.

RAG (Retrieval-Augmented Generation) helps with all three, and the idea is almost suspiciously simple: find the right information first, put it in front of the model, then ask the question. The model doesn't change. You're handing it an open book.

When the "book" is too big to hand over whole, you need a few more pieces:

  • Chunking: cut the documents into smaller pieces.
  • Embeddings: turn each piece into a list of numbers that captures its meaning, so pieces that mean similar things land close together.
  • A vector database: stores those numbers so you can quickly find the pieces nearest a question.
  • Keyword search: meaning-based search can miss exact tokens like IDs, error codes, or field names. Keyword search (BM25) catches them. Running both together is hybrid search.

Where I'd already seen this at work

The strange part of today was recognising the textbook. Three agents I'd worked on were already doing pieces of this, I just didn't have the vocabulary for it at the time.

BILL: a developer chatbot that invented API fields

BILL's developer chatbot answered API questions, but it sometimes made up fields that didn't exist, or gave endpoint examples that didn't match the real API.

  • BILL's API specification is about 800,000 characters, far too big to hand the model all at once.
  • The plan was to split the spec one piece per API operation. That is chunking along the document's own structure.
  • The agent then worked in two steps. Discover: find the operation that matches the developer's question. Verify: look up that operation's exact definition (parameters, request body, responses) before answering.
  • The rule: no technical detail without a successful lookup, and if the docs and the spec disagree, the spec wins. Later I fixed wrong documentation links by rebuilding each link from the endpoint details.
Something that didn't work, and what it taught me

I first tried asking an LLM to enrich every endpoint while building the index (about 300 endpoints, 10 workers at once). It hit rate limits, with waits of 39 to 293 seconds, and the job timed out at its 120-second budget. The lesson: be careful about calling an LLM for every item during indexing. If you must, put it behind a queue, retries with backoff, and a time budget.

Nutanix: build logs too big to search

Nutanix's root-cause-analysis agent needed to read build logs attached to support tickets. Some logs were up to 100 MB, and files over 1 MB weren't indexed automatically, so the agent couldn't search them at all.

  • I built a chunker that downloads the log from the ticket and splits it into ~60 KB pieces, saving each as a searchable article with tags. A 100 MB log became about 1,700 articles.
  • Creating that many articles meant many API calls, so the bot ran into rate limits. A change was proposed to raise its limit from 2,000 to 10,000 requests per minute.

What clicked today: the platform doesn't turn a 60 KB article into one embedding. It splits each article again into smaller passages before embedding, and shows the full article when one passage matches. So without naming it, I had built two-level chunking: my code made the big pieces, the platform made the small ones.

Camping World: when search isn't the right tool

For a Camping World agent, a user wanted to find one specific chat. Search returned the top 10 of 223 chat rooms, but the one they needed ranked #143, so it never showed up. I switched that part to a database query (SQL).

The lesson is worth stating plainly: search gives you the best matches, not a complete list. For "find all of X," use a query, not retrieval.

What I built today

I wanted to see these ideas with real numbers rather than vibes, so I built a small project: rebuild each layer of a RAG system, measure it, and review how it would scale.

Corpus: FastAPI docs · 114 pagesEval: 30 questionsScored on: Recall@5 · MRR · context size

Every one of the 30 test questions carries a short "evidence" phrase that must appear in a retrieved result for it to count as found. The scores: Recall@5 asks whether the answer was in the top 5 results; MRR asks how high up it ranked; context size is how much text would be sent to the model.

Project 00: write the test first

Before building anything, I wrote the 30 questions and a small checker that confirms every answer really exists in the documents. Then I tried the simplest possible approach: keyword search over whole pages. It found every answer (Recall@5 = 1.00), but sent about 38,500 characters to the model per question. That is like answering one question by handing someone five entire chapters.

Project 01: five ways to cut the documents

I cut the same pages five different ways and tested each with both keyword search (BM25) and meaning search (the BGE-small embedding model).

What the results taught me

  • Smaller pieces cost far less. Cutting the pages sent 9 to 18 times less text and still found 63% to 80% of answers. For BILL the full spec was too big to use; for Nutanix the logs couldn't even be indexed. Cutting down wasn't optional, it was the whole game.
  • Cutting along the document's own structure won. Splitting at section headings, with the heading sitting on top of each piece, beat everything with both kinds of search. Each piece is one complete idea with a name. That is the same move as splitting BILL's spec one operation at a time. My Nutanix chunker split purely by size, so next time I'd split logs at build stages or error blocks, with a label like "build 412 > test stage > error."
  • Meaning search usually beat keyword search, because people ask questions in different words than the docs use. But keyword search still earns its place for exact values: build numbers, error codes, field names like billCurrency.
  • Neither search was perfect, and they missed different questions. That is exactly why combining them (hybrid search) works so well in practice, and it's what I'll test next.
  • More pieces means more cost. The "small pieces" method made 4,584 chunks, about four times more to embed and store. Same thing I saw at Nutanix: more chunks, more API calls, more rate limits.
  • Running a model during indexing is slow. Cutting by topic change was the slowest method, because it runs the embedding model on every sentence. Same lesson as my BILL indexing attempt.
  • The test set was the most important part. Without the 30 questions I'd only be guessing which method was better. For BILL I'd asked for a bug bash and example questions with expected answers; for Nutanix I reported roughly 96% accuracy, and now I know how I'd measure a number like that more carefully: a known failure, the exact error line I expect to find, and a score for each.
The idea, in one sentence

RAG is just giving the model the right page before you ask the question. Everything hard about it is logistics: cut the documents along their own structure, label every piece, search by meaning and by keyword together, and never change any of it without a test set to tell you whether you made things better or worse.

What I'd do differently now

  • Split by structure, not just size: logs by stage, API specs by operation, docs by heading. Give every piece a label.
  • Use keyword and meaning search together, not one or the other.
  • Measure before and after any change, even with a small set of questions.
  • Keep LLM calls out of indexing unless they're queued, retried, and time-limited.
