Prefix Sums: compute once, answer instantly

Asmita Hanchate· Nov 21, 2026· 7 min read· Prefix Sums

The sliding window on Day 3 kept a running total as it moved, adding what entered and dropping what left. Prefix sums are the calmer cousin of that idea. Instead of sliding one window, you walk the array once and write down the running total at every position. After that, the sum of any range at all is a single subtraction. You pay O(n) once, up front, so that every question you ask afterwards costs O(1).

Here's the one equation the whole pattern rests on. Let prefix[i] be the sum of nums[0] through nums[i]. Then the sum of the range from left to right is:

sum(left..right) = prefix[right] - prefix[left - 1]

Everything up to right, minus everything before left, leaves exactly the middle. A range becomes a subtraction. Once you see a problem asking about sums over ranges, this is the tool to reach for.

01Range Sum Query, Immutable

LeetCode 303 · the pattern in its purest form

You get an array and then many queries, each asking for the sum between two indices. Summing the range fresh each time is O(n) per query. The word immutable in the title is the hint: the array never changes, so you can precompute every running total once in the constructor and then answer each query by subtraction.

class NumArray:
    def __init__(self, nums: List[int]):
        self.prefix = []
        total = 0
        for n in nums:
            total += n
            self.prefix.append(total)        # prefix[i] = sum of nums[0..i]

    def sumRange(self, left: int, right: int) -> int:
        preRight = self.prefix[right]
        preLeft = self.prefix[left-1] if left > 0 else 0   # nothing before index 0
        return preRight - preLeft
Build O(n)Query O(1)Space O(n)

The only edge case is left == 0, where there's no prefix[left - 1] to subtract, so the "before" sum is just zero. This split, a one-time build and then cheap repeated queries, is the shape to recognise: it's the same bargain as caching, pay once to read many times.

02Find Pivot Index

LeetCode 724 · prefix meets postfix

Find the index where the sum of everything to its left equals the sum of everything to its right. Build the running total from the left (prefix) and from the right (postfix). Because both include nums[i] itself, the pivot is simply where they match.

class Solution:
    def pivotIndex(self, nums: List[int]) -> int:
        prefix, postfix, total = [], [], 0
        for i in range(len(nums)):
            total += nums[i]
            prefix.append(total)
        total = 0
        for i in range(len(nums)-1, -1, -1):   # build the right-side total backwards
            total += nums[i]
            postfix.append(total)
        postfix.reverse()
        for i in range(len(nums)):
            if prefix[i] == postfix[i]:
                return i
        return -1
Time O(n)Space O(n)

There's a leaner version that drops the second array entirely: keep the whole total, walk left to right with a running_sum, and at each index compare the left part to what's left over. That one is O(1) space. Worth knowing both, because the two-array version is the one you can read at a glance, and the single-pass version is the one you reach for when memory is tight.

        # O(1) space version
        total = sum(nums)
        running_sum = 0
        for i in range(len(nums)):
            running_sum += nums[i]
            if running_sum == total:          # left+self == right+self
                return i
            total -= nums[i]
        return -1

03Product of Array Except Self

LeetCode 238 · the same skeleton, with products

Return an array where each slot holds the product of every number except the one at that slot, and you're not allowed to divide. The prefix idea transfers straight across: prefix[i] is the product of everything to the left of i, postfix[i] the product of everything to the right, and the answer is the two multiplied. The optimized version skips the extra arrays by writing the left products straight into the result, then walking back through with the right products.

class Solution:
    def productExceptSelf(self, nums: List[int]) -> List[int]:
        result = [1] * len(nums)
        pre = 1
        for i in range(len(nums)):      # left pass: product of everything before i
            result[i] = pre
            pre *= nums[i]
        post = 1
        for i in range(len(nums)-1, -1, -1):   # right pass: multiply the right product in
            result[i] *= post
            post *= nums[i]
        return result
Time O(n)Space O(1) extra · result doesn't count

I like this one because it shows the prefix idea isn't really about addition. It's about carrying a running aggregate so that each position already knows everything around it. Swap the sum for a product and the whole scaffold still stands. Two passes, no division, no extra memory beyond the answer.

04Subarray Sum Equals K

LeetCode 560 · prefix sums meet the hash map

Count how many contiguous subarrays add up to k. This is the one that made the whole pattern click, because it's really Day 1's Two Sum wearing a disguise. A subarray from i+1 to j sums to k exactly when prefix[j] - prefix[i] == k, which rearranges to prefix[i] == currSum - k. So as I walk the array keeping a running sum, I ask the same question as Two Sum: have I already seen the running sum I'd need? A hash map of running-sum counts answers it instantly.

class Solution:
    def subarraySum(self, nums: List[int], k: int) -> int:
        res, currSum = 0, 0
        prefixSums = {0: 1}                    # sum 0 seen once: the empty prefix
        for n in nums:
            currSum += n
            diff = currSum - k                 # the earlier prefix I'd need
            res += prefixSums.get(diff, 0)       # how many times I've seen it
            prefixSums[currSum] = 1 + prefixSums.get(currSum, 0)
        return res
Time O(n)Space O(n)

The {0: 1} base case matters: a running sum of zero has "happened once" before the array even starts, which is what lets a subarray beginning at index 0 get counted. And here's the part I want to remember most: why this can't be a sliding window. The numbers can be negative or zero, so a running sum getting "too big" doesn't mean shrinking from the left will help, and a window can only track one subarray ending at each index, not count several. When negatives are in play, the window breaks and prefix-sum-plus-hashmap is the move. (This is one I've flagged to come back and re-solve from scratch, because the rearrangement is the kind of thing that's obvious while reading and slippery a week later.)

The pattern, in one sentence

When a problem asks about sums (or products) over ranges of an array, precompute running totals so every range turns into one subtraction. Fixed queries on an unchanging array want a prefix array built once. Left equals right wants prefix against postfix. Counting subarrays that hit a target wants prefix sums plus a hash map, which is Two Sum all over again.

Why I'm writing this one down

Four days in, the same instinct keeps returning in new costumes: don't redo work you've already done. Day 1 remembered values in a hash map. Day 3 carried a window's total as it slid. Today precomputes every running total so a range costs one subtraction. The prettiest moment was the last problem folding all the way back to the first: once the data is the running sum instead of the raw values, "find a subarray that sums to k" and "find two numbers that add to target" are the exact same question, answered by the exact same hash map.
