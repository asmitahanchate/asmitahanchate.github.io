What I learned about RAG, and how it connects to my work

Asmita Hanchate· Nov 20, 2026· 9 min read· RAG

I learned something new today, and I want to write it down while it's fresh. I'm an Applied AI Engineer at DevRev, working with S&P Global, Nutanix, Camping World and BILL. My work covers the whole path from data to answer: ingestion pipelines, retrieval and search, the agents on top, and the evaluation that tells us whether they work in production.

Again and again, I've seen the same lesson: when an AI system gives a wrong answer, the model is often fine. The system never gave it the right information. So today I went back over the fundamentals of retrieval properly, and built a small project to test them with real numbers. Here's what I found, and how it connects to my work.

The basics, in plain words

Language models have three recurring problems:

  • They can make things up. This is hallucination.
  • They can only read so much at once. That limit is the context window.
  • They don't know your private data. They only know what they were trained on.

RAG (Retrieval-Augmented Generation) helps with all three, and the idea is simple: find the right information first, put it in front of the model, then ask the question. The model stays the same. You're handing it an open book.

When the "book" is too big, you need a few more pieces:

  • Chunking: cut the documents into smaller pieces.
  • Embeddings: turn each piece into a list of numbers that represents its meaning, so pieces with similar meaning end up close together.
  • A vector database: stores those numbers so you can quickly find the pieces closest to a question.
  • Keyword search: meaning-based search can miss exact words like IDs, error codes or field names. Keyword search (BM25) finds them. Using both together is hybrid search.

Where these ideas show up in my work

The part that struck me today was recognising the textbook. Across the agents I've shipped, these ideas were already load-bearing, I just didn't always have the vocabulary for them at the time.

01BILL

I built a Retrieval-Augmented Generation pipeline for BILL (NYSE-listed fintech) over an 800K-character OpenAPI spec using two-stage retrieval and LLM-free indexing, cutting hallucinations from ~30–40% to under 2% and context tokens by ~70% at sub-second latency.

  • Two-stage retrieval: /discover ranks API operations for a natural-language question, and /get_endpoint_details returns one operation's full schema. The assistant verifies against the schema before answering.
  • Why LLM-free indexing: my first attempt enriched 300 endpoints with an LLM (10 workers) and hit rate-limit backoffs of up to 293 seconds against a 120-second runtime limit. Indexing by API operation, without an LLM, was faster and reliable.
  • Connection to today: this is chunking by the document's own structure, one operation per piece.

02Nutanix

I architected memory-based infrastructure for agents at Nutanix with Bring-Your-Own-Agent / Knowledge-Base support, letting users connect any system (Jira, Jenkins, AWS, GCP, Azure and more) as agent memory through an event-driven ingestion pipeline that chunks build logs up to 200 MB for hybrid BM25 + vector search.

I reduced Nutanix build-failure triage from up to 7 hours to under 30 seconds with ~96% root-cause accuracy across 15–30 failed builds a day via signal-based text-to-SQL retrieval, auto-routing each failure to its owner as a Jira ticket.

  • Connection to today: logs are split into ~60 KB segments to stay under a 1 MB indexing limit, and the platform splits each segment again into smaller passages before embedding. That's two-level chunking: big segments for context, small passages for precise matching.

03Camping World

I engineered an enterprise search system for Camping World (~13K employees) unifying Outlook, Teams, Jira, Confluence and Asana behind one AI assistant with permission-scoped retrieval, raising result coverage from ~4.5% to 100% by routing exact lookups to deterministic SQL.

I scaled Camping World's data agents with a summary-table caching layer over tens of millions of Snowflake records, replacing ~32 s warehouse scans that timed out agent workflows with pre-aggregated reads.

  • Connection to today: ranked search returned the top 10 of 223 chat rooms, and the one a user needed was #143. Search gives you the best matches, not a complete list. For "find all of X," use SQL.

04S&P Global

I designed a unified knowledge layer for S&P Global that syncs data from any source (for example, Azure DevOps) for search and SQL querying, shrinking quarterly program (PI) planning from 1 week to a few hours for RTEs, scrum masters and PMs.

05EvalFrame

I co-built EvalFrame, an LLM evaluation framework that auto-generates test suites, replays multi-turn conversations against live agents and scores them with a weighted LLM-as-judge rubric, plus a downvote-to-ticket feedback loop.

The common thread

In every one of these, the hard part wasn't the model. It was getting the right data, in the right shape, to the right place, reliably and with the right permissions.

What I built today

I wanted to see these ideas with real numbers rather than vibes, so I built a small project: rebuild each layer of a RAG system, measure it, and review how it would scale. The code is on GitHub.

Corpus: FastAPI docs · 114 pagesEval: 30 questionsScored on: Recall@5 · MRR · context size

Every one of the 30 test questions carries a short "evidence" phrase that must appear in a retrieved result for it to count as found. The scores: Recall@5 asks whether the answer was in the top 5 results; MRR asks how high up it ranked; context size is how much text would be sent to the model.

Project 00: write the test first

Before building anything, I wrote the 30 questions and a small checker that confirms every answer really exists in the documents. Then I tried the simplest possible approach: keyword search over whole pages. It found every answer (Recall@5 = 1.00), but sent about 38,500 characters to the model per question. That is like answering one question by handing someone five entire chapters.

Project 01: five ways to cut the documents

I cut the same pages five different ways and tested each with both keyword search (BM25) and meaning search (the BGE-small embedding model).

What the results taught me

  • Smaller pieces cost much less. Cutting the pages sent 9 to 18 times less text and still found 63% to 80% of the answers. For BILL, the full spec was too big to use. For Nutanix, the raw logs couldn't even be indexed. Cutting things down wasn't optional.
  • Cutting along the document's own structure worked best. Splitting at section headings, with the heading on top of each piece, won with both kinds of search. Each piece is one complete idea with a name. That's the same idea as splitting BILL's spec one operation at a time. For logs, the next improvement I'd try is splitting at build stages or error blocks, with a label like "build 412 > test stage > error."
  • Meaning search usually beat keyword search. People ask questions in different words than the documents use, and meaning search handles that well. Keyword search still matters for exact values like build numbers, error codes, or field names like billCurrency.
  • Neither search was perfect, and they missed different questions. That's why combining them (hybrid search) works so well in practice, and it's what I'll test next.
  • More pieces means more cost. The "small pieces" approach made 4,584 pieces, about four times more to embed and store. I saw the same thing at Nutanix: more segments meant more API calls and more rate-limit planning.
  • Running a model during indexing is slow. Cutting by topic change was the slowest method, because it runs the embedding model on every sentence. It's the same lesson as BILL: LLM-free indexing was faster and more reliable than calling a model for every item.
  • Testing is the most important part. Without the 30 questions, I would only be guessing which method was better. With EvalFrame, an LLM judge scores whole conversations. This project showed me that simple, mechanical checks ("is the answer actually in the result?") are a good partner to that.

What I'm taking away

  • Split by structure, not just size: logs by stage, API specs by operation, docs by heading. Give every piece a label.
  • Use keyword and meaning search together.
  • Measure before and after any change, even with a small set of questions.
  • Keep LLM calls out of indexing, unless they're queued, retried, and time-limited.
