Linked Lists: a handful of moves that keep combining

Asmita Hanchate· Nov 23, 2026· 9 min read· Linked Lists

For four days the data sat in a neat indexable row. I could ask for nums[i], I knew the len, and I could jump anywhere I liked. A linked list takes all of that away. Each node knows one thing only: who comes next. No index, no length, no going backward. What you hold is a single pointer, and the whole game becomes moving pointers carefully enough that you never lose the rest of the list. What surprised me today is how few distinct moves that actually takes. Three small ones, and then the harder problems are just those three snapped together.

The nodes look like this the whole way through, so I'll stop repeating it:

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next       # the only way out of a node

01Reverse a list

LeetCode 206 · the move everything else borrows

Reversing is the first move, and it's the one I reuse the most, so it's worth slowing down on. The trap is obvious once you hit it: the moment you point a node's arrow backward, you've thrown away its link to the rest of the list. So before flipping anything, you save where you were going. Three pointers do it, in this order every time: remember next, flip, then shuffle both pointers forward.

class Solution:
    def reverseList(self, head: Optional[ListNode]) -> Optional[ListNode]:
        prev, curr = None, head
        while curr:
            temp = curr.next      # 1. remember the rest of the list
            curr.next = prev      # 2. flip this node's arrow backward
            prev = curr           # 3. prev catches up
            curr = temp           # 4. curr moves on
        return prev               # the old tail is the new head
Time O(n)Space O(1)

When the loop ends, curr has run off the end and prev is sitting on what used to be the last node, which is now the front. That one detail, prev ends up as the new head, is the thing to hold onto, because every problem below reverses something and then reaches for prev.

02Merge two sorted lists

LeetCode 21 · the dummy node

Given two sorted lists, stitch them into one sorted list. The logic is easy, pick the smaller head and advance that list, but there's an annoying wrinkle: the very first node is a special case, because the result doesn't have a head yet. The fix is a trick I now reach for by reflex. Start with a throwaway dummy node so the list always has a fixed handle to build from, and return dummy.next at the end.

class Solution:
    def mergeTwoLists(self, list1, list2) -> Optional[ListNode]:
        dummy = node = ListNode()        # a fixed handle on the merged list
        while list1 and list2:
            if list1.val < list2.val:
                node.next = list1
                list1 = list1.next
            else:
                node.next = list2
                list2 = list2.next
            node = node.next
        node.next = list1 or list2       # attach whatever's left, in one line
        return dummy.next                # skip the dummy, hand back the real head
Time O(m + n)Space O(1) · reuses the nodes

Two small things I want to keep. node.next = list1 or list2 leans on Python returning the first truthy value, so when one list empties, the whole remaining tail gets attached at once (it's already sorted, no need to walk it). And nothing is copied: the merged list is the same nodes, just re-pointed. That reuse is the quiet theme of the whole day.

03Two speeds: the fast and slow pointer

LeetCode 876 and 141 · one trick, two questions

Here's the move that unlocks the second half of the list. Run two pointers at once: slow takes one step, fast takes two. By the time fast falls off the end, slow has only gone halfway, so it's sitting on the middle. That's the entire idea behind finding the middle in a single pass, without ever knowing the length.

class Solution:
    def middleNode(self, head) -> Optional[ListNode]:
        slow = fast = head
        while fast and fast.next:
            slow = slow.next
            fast = fast.next.next      # twice the pace
        return slow                    # fast hit the end, so slow is the middle
Time O(n)Space O(1)

Now the same two speeds answer a completely different question: does this list loop back on itself? If there's no cycle, fast runs off the end like before. But if there is a cycle, fast can't escape, it keeps lapping the loop, and because it gains exactly one step on slow every iteration, it has to eventually land on the same node. The pointers meeting is the proof of a cycle. This is Floyd's algorithm, and it costs no extra memory, where the obvious "keep a set of visited nodes" approach costs O(n).

class Solution:
    def hasCycle(self, head) -> bool:
        slow = fast = head
        while fast and fast.next:
            slow = slow.next
            fast = fast.next.next
            if slow == fast:          # they met, so fast is lapping a loop
                return True
        return False                    # fast reached the end, no loop
Time O(n)Space O(1)

Same six lines, swap "return slow" for "did they collide," and one tool reads the middle or detects a loop. That reuse is exactly the pattern I keep betting on.

04When the moves combine: Twin Sum, then Reorder

LeetCode 2130 and 143 · find the middle, reverse, then walk together

This is where the day paid off. Maximum Twin Sum pairs the first node with the last, the second with the second-last, and so on, and asks for the largest pair sum. The easy version copies the values into an array and runs two pointers from both ends, which is Day 2 all over again but costs O(n) space. The version I'm prouder of does it in O(1) by combining two moves from above: use the fast and slow pointer to reach the middle, and reverse the first half while you're walking there. When fast hits the end, prev is the reversed first half and slow is the second half, both facing the middle, so walking them forward together pairs each node with its twin.

class Solution:
    def pairSum(self, head) -> int:
        slow, fast = head, head
        prev = None
        while fast and fast.next:      # find the middle AND reverse the first half
            fast = fast.next.next
            temp = slow.next
            slow.next = prev
            prev = slow
            slow = temp
        res = 0
        while slow:                    # prev walks the reversed front, slow the back
            res = max(res, prev.val + slow.val)
            prev = prev.next
            slow = slow.next
        return res
Time O(n)Space O(1)

Reorder List is the fuller version of the same idea, and it's the problem that made the whole day click into place. It wants the list laced together as first, last, second, second-last, and so on, done in place. That's three moves in sequence, each one already written above: find the middle, reverse the second half, then weave the two halves together one node at a time.

class Solution:
    def reorderList(self, head) -> None:
        slow, fast = head, head
        while fast and fast.next:          # 1. find the middle (move 03)
            slow = slow.next
            fast = fast.next.next

        second = slow.next                     # 2. cut, then reverse the back half (move 01)
        prev = slow.next = None
        while second:
            temp = second.next
            second.next = prev
            prev = second
            second = temp

        first, second = head, prev             # 3. weave front and reversed-back together
        while second:
            tmp1, tmp2 = first.next, second.next
            first.next = second
            second.next = tmp1
            first, second = tmp1, tmp2
Time O(n)Space O(1)

An honest note, because I keep one of these every day. My first pass at Reorder List didn't actually reorder anything. I copied the values into an array, built the interleaved order in a second array, and printed it, which looks right in the console and is completely wrong: the problem asks you to rewire the real nodes in place, and my version also quietly dropped the middle value on odd-length lists. I kept that first attempt in the file next to the real one. Seeing them side by side is the clearest reminder that with linked lists, producing the right values is not the same as moving the right pointers.

05The same trick, off the list entirely

LeetCode 287 · Find the Duplicate Number

The one that genuinely made me grin. You're handed an array of n + 1 numbers, each between 1 and n, and there's exactly one duplicate. Find it without sorting, without a hash set, and without modifying the array. All three easy doors are locked. The unlock is to stop seeing an array and see a linked list hiding inside it: read each value as a pointer, i leads to nums[i]. Because two different indexes hold the same value, two arrows point at the same place, which is exactly a cycle, and the node where the loop begins is the duplicate.

class Solution:
    def findDuplicate(self, nums: List[int]) -> int:
        slow = fast = 0
        while True:                   # phase 1: two speeds, until they meet in the loop
            slow = nums[slow]
            fast = nums[nums[fast]]
            if slow == fast:
                break
        slow2 = 0                      # phase 2: from the start and the meeting point,
        while True:                   # step together; they meet at the loop's entrance
            slow = nums[slow]
            slow2 = nums[slow2]
            if slow == slow2:
                return slow
Time O(n)Space O(1)nums untouched

Phase one is the cycle detection from move 03. Phase two is the piece of Floyd's I hadn't needed before: once the two pointers have met somewhere inside the loop, restarting one pointer from the very beginning and stepping both at the same pace lands them together precisely at the entrance to the loop, and that entrance is the repeated value. I'm not going to pretend the proof of phase two was obvious to me on sight, it wasn't, but the shape of it is worth memorizing even before the proof fully lands: meet inside the loop, then walk one up from the start to find the door.

The pattern, in one sentence

A linked list gives you one pointer and one direction, so learn a few pointer moves cold and let them combine. Reverse is save-next, flip, shuffle forward, and prev is your new head. Fast and slow finds the middle in one pass and detects a cycle with no extra memory. A dummy node kills the first-node special case. The hard problems (Reorder, Twin Sum, Find the Duplicate) aren't new tricks, they're those three in a row.

Why I'm writing this one down

Days 1 through 4 were all one quiet idea in different clothes: don't redo work you've already done. Day 5 is a different lesson, and it's the one I needed. The problems that looked hardest, reorder the list, pair the twins, find the duplicate, turned out to have no new ingredient in them at all. They were reverse, plus two speeds, plus a careful weave, stacked. The skill the day actually tested wasn't inventing anything. It was trusting that a move I already knew would still hold when I leaned a second and a third move on top of it. And the prettiest moment, again, was a callback: Find the Duplicate takes the cycle detection built for pointers and runs it on a plain array, which means the linked-list tool reached all the way back and solved an array problem from Week 1.
