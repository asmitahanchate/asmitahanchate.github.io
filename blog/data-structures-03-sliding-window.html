The Sliding Window: one pass, no re-reading

Asmita Hanchate· Nov 19, 2026· 7 min read· Sliding Window

Day 1 was about remembering the array with a hash table. Day 2 was about walking it from both ends with two pointers converging inward. Day 3 keeps the two pointers but changes their choreography: now they move the same direction, and the stretch of array sitting between them, the window, is what holds the answer. The whole trick is that the left pointer never walks backwards, so even though there are two loops on the page, each element is touched a constant number of times and the work stays O(n).

Here's the shape I kept seeing. A brute-force answer to "find the best contiguous run" re-examines every run from scratch: start here, scan forward, add it all up, start one over, scan again. That's O(n²), and most of it is re-adding numbers I already added a step ago. A window fixes that by keeping a running view. When the window moves, I don't rebuild it. I just account for the one element that entered on the right and the one that left on the left.

There are two flavors, and telling them apart is most of the battle:

  • Fixed window: the size is locked at some k. Every step, one element enters and one leaves, so the window slides without ever changing length.
  • Variable window: the size breathes. The right pointer grows the window; a condition decides when the left pointer shrinks it. You're hunting for the longest or shortest window that still satisfies something.

01Number of Subarrays, average ≥ threshold

LeetCode 1343 · the fixed window, and why you never re-sum

Count the length-k subarrays whose average is at least threshold. (This one and the unfinished problem below live in the fixed-size folder.) The naive version sums every window independently, which is O(n · k). But neighbouring windows overlap in all but two elements, so re-summing throws away almost everything you just computed. Instead, carry a running currSum: add the number entering on the right, check the window, then subtract the number leaving on the left.

class Solution:
    def numOfSubarrays(self, arr: List[int], k: int, threshold: int) -> int:
        result = 0
        currSum = sum(arr[:k-1])          # pre-load the first k-1 elements
        for left in range(len(arr) - k + 1):
            currSum += arr[left + k - 1]     # the newcomer on the right: now exactly k
            if (currSum / k) >= threshold:
                result += 1
            currSum -= arr[left]           # drop the leaver: back to k-1 for next step
        return result
Time O(n)Space O(1)

This is Day 1's lesson in disguise: don't recompute what you can carry forward. The window is a tiny cache of one number, and sliding it costs one addition and one subtraction no matter how big k is. (Small aside I liked: comparing currSum >= k * threshold instead of dividing avoids floating-point entirely and says the exact same thing.)

02Minimum Size Subarray Sum

LeetCode 209 · the variable window in its clearest form

Find the shortest contiguous subarray whose sum is at least target. Now the window can't be a fixed size, because I don't know how long "shortest" is until I find it. So the window breathes: the for loop grows it to the right, and the while loop shrinks it from the left the moment it's valid, trying to make it smaller while it still clears the target.

class Solution:
    def minSubArrayLen(self, target: int, nums: List[int]) -> int:
        length = float("inf")
        left, total = 0, 0
        for right in range(len(nums)):
            total += nums[right]               # grow on the right
            while total >= target:              # valid? try to shrink
                length = min(right - left + 1, length)
                total -= nums[left]
                left += 1
        return 0 if length == float("inf") else length
Time O(n)Space O(1)

The while loop is what scared me at first, because a loop inside a loop looks like O(n²). It isn't. The left pointer only ever moves forward, and it can't pass the right pointer, so across the whole run it advances at most n times total. Each index enters the window once and leaves once. That "enters once, leaves once" accounting is the thing to hold onto; it's what makes every honest sliding window O(n) even with a nested loop on screen.

03Longest Substring Without Repeating Characters

LeetCode 3 · a window made of a set

Find the longest substring with no repeated character. The window here isn't a sum, it's a set of the characters currently inside it, which is Day 1 showing up again. Before I let a new character in on the right, I shrink from the left until the duplicate is gone, so the window always holds unique characters by construction.

class Solution:
    def lengthOfLongestSubstring(self, s: str) -> int:
        window = set()
        left, length = 0, 0
        for right in range(len(s)):
            while s[right] in window:         # shrink until the clash is gone
                window.remove(s[left])
                left += 1
            window.add(s[right])
            length = max(length, right - left + 1)
        return length
Time O(n)Space O(min(n, m)) · m = charset size

Same O(n) reasoning as problem 2: each character gets added to the set once and removed once, so the inner while does O(n) work in total, not per step. What changed is only what the window keeps track of. A sum answers "how much"; a set answers "what's in here right now." The window is just a container, and you pick the container that makes the question cheap.

04Longest Repeating Character Replacement

LeetCode 424 · the window that slides but never shrinks

You may replace up to k characters; find the longest substring you can make all one letter. The count of characters you'd have to replace is window length − (count of the most frequent letter). If that exceeds k, the window is invalid. The subtle part, and the one that took me a second: this uses an if, not a while.

class Solution:
    def characterReplacement(self, s: str, k: int) -> int:
        count = {}
        result, left = 0, 0
        for right in range(len(s)):
            count[s[right]] = 1 + count.get(s[right], 0)
            if (right - left + 1) - max(count.values()) > k:
                count[s[left]] -= 1
                left += 1
            result = max(result, right - left + 1)
        return result
Time O(26 · n) = O(n)Space O(1) · at most 26 keys

Why if and not while? Because I never need a window shorter than the best I've already found. If the current window goes invalid, I slide it forward by one, keeping the same length, and carry on. It can only ever grow past the record, never shrink below it, so the answer is just the largest length the window ever reached. That's a different mental model from problem 2, where shrinking was the whole point, and noticing the difference is what made the pattern click for me rather than feeling like four unrelated tricks.

The pattern, in one sentence

When the answer is a contiguous run and brute force keeps re-scanning overlapping pieces, slide a window instead: move the right pointer to grow it, account only for what enters and leaves, and let the question decide the left pointer. Fixed size when the length is given; variable size when you're hunting for the longest or shortest valid run. Each index enters and leaves once, so it's one pass.

The one I haven't finished yet

I want this series to be honest about where I'm still stuck, so: Sliding Subarray Beauty (LeetCode 2653). My first instinct was to keep the window in a list, sort it every step, and read the x-th smallest value. It's correct, and it passes 708 of 717 test cases before timing out.

class Solution:
    def getSubarrayBeauty(self, nums: List[int], k: int, x: int) -> List[int]:
        currList, result = [], []
        left = 0
        for right in range(len(nums)):
            currList.append(nums[right])
            currList.sort()                      # this is the O(k log k) tax, every step
            if (right - left + 1) == k:
                result.append(currList[x-1] if currList[x-1] < 0 else 0)
                currList.remove(nums[left])
                left += 1
        return result
Time O(n · k log k)Space O(k) · too slow

The bug isn't correctness, it's that I broke the whole point of a window. Re-sorting every step is exactly the "re-read what I already knew" habit the pattern exists to kill. The fix I've written myself a note about: the values are tiny, only −50 to 50, so instead of sorting I can keep a tally, a count of how many times each value is in the window. To find the x-th smallest I count up from −50 until I've passed x numbers. That's a fixed 101-bucket scan per step, O(n) overall. I'll come back and write the counting version properly before I call this one done.

Why I'm writing this one down

Three days in, the throughline is clearer than any single trick. Day 1: stop re-reading the array, remember it. Day 2: stop checking every pair, walk from both ends with a reason. Day 3: stop rebuilding every window, carry one forward and only touch what changes. They're the same instinct wearing different clothes, which is "don't redo work you've already done." The sliding window just makes that instinct physical: there's a literal left edge that is never, ever allowed to walk backwards.
