Binary Search: the real skill is which half you throw away

Asmita Hanchate· Nov 24, 2026· 8 min read· Binary Search

Everybody learns binary search the same friendly way: the array is sorted, look at the middle, go left if your target is smaller and right if it's bigger. That version is easy, and it's also the least interesting thing binary search can do. The three problems I did today all skip the friendly case. None of them is a plain "is it here." The thread running through them is the part nobody emphasises when they teach the easy version: every step, you delete half the array, and the entire difficulty is proving that the half you're deleting cannot possibly contain the answer. Get that proof wrong and you either skip past the answer or loop forever.

This is the same move Day 2 was built on. Two pointers worked because, on sorted input, I could prove which pointer to move so I never stepped over the answer. Binary search is that idea with the volume turned up: sorted input lets me prove which half to throw away, so I never read it at all. That's where the O(log n) comes from. The skill isn't the loop, it's the argument inside the if.

01Find First and Last Position

LeetCode 34 · binary search as a boundary finder

The array is sorted and the target can repeat, and I need the first and last index where it appears, in O(log n). The honest thing to admit first: plain binary search finds a match, not the leftmost or rightmost one, because the moment it lands on the value it stops. The fix reframes what binary search is for. Don't stop on a match. On a match, record it and keep searching the side you still care about. One pass can only lean one way, so I run it twice: once leaning left for the first occurrence, once leaning right for the last.

class Solution:
    def searchRange(self, nums: List[int], target: int) -> List[int]:
        first, last = float("inf"), float("-inf")

        left, right = 0, len(nums) - 1        # pass 1: find the FIRST match
        while left <= right:
            mid = (left + right) // 2
            if nums[mid] < target:
                left = mid + 1
            elif nums[mid] > target:
                right = mid - 1
            else:
                first = min(first, mid)
                right = mid - 1               # a match, but keep going left

        left, right = 0, len(nums) - 1        # pass 2: find the LAST match
        while left <= right:
            mid = (left + right) // 2
            if nums[mid] < target:
                left = mid + 1
            elif nums[mid] > target:
                right = mid - 1
            else:
                last = max(last, mid)
                left = mid + 1                # a match, but keep going right

        return [first, last] if first != float("inf") else [-1, -1]
Time O(log n)Space O(1)

Two details I had to be careful with. The "did we ever find it" check has to be first != inf, not first > 0, because index 0 is a perfectly valid first position and first > 0 would throw it away. And the takeaway that outlasts this one problem: binary search doesn't only answer "is the target here," it can hunt for a boundary, the edge where a condition flips from false to true. Keep searching past the match, toward the edge you want.

02Find Minimum in a Rotated Sorted Array

LeetCode 153 · searching for structure, not a value

A sorted array was rotated at some unknown point, so [1,2,3,4,5] might now be [3,4,5,1,2], and I need the minimum in O(log n). There's no target here at all, which is the whole mental shift: I'm not searching for a value I was handed, I'm searching for a structural feature. The minimum is the one element that broke the ascending order, the single number smaller than both of its neighbours. When I'm not standing on it, I steer toward the half that goes downhill, because the drop is where the minimum lives.

class Solution:
    def findMin(self, nums: List[int]) -> int:
        left, right = 0, len(nums) - 1
        n = len(nums)
        while left <= right:
            mid = (left + right) // 2
            prev, nxt = (mid - 1) % n, (mid + 1) % n
            if nums[mid] < nums[prev] and nums[mid] < nums[nxt]:
                return nums[mid]               # smaller than both neighbours = the min
            elif nums[left] > nums[mid]:
                right = mid - 1               # the drop is on the left
            elif nums[right] < nums[mid]:
                left = mid + 1                # the drop is on the right
            else:
                right = mid - 1               # no drop in view: already sorted, min is at the start
        return nums[0]                      # 1-element array never enters a comparison
Time O(log n)Space O(1)

My honest note for the day lives in that last else. My first version only had the two "which side is unsorted" branches, and on an array that was already sorted (or a sub-window with no drop left in it) neither branch fired cleanly, the pointers stopped moving, and it timed out, an infinite loop dressed up as a wrong answer. Adding the else: right = mid - 1 is the fix: when no descent is visible, everything in view is ascending, so the smallest thing is at the left end and shrinking the window from the right is always safe. A binary search that can reach a state where it moves neither pointer is not slow, it's broken. Every branch has to make the window strictly smaller.

03Search in a Rotated Sorted Array

LeetCode 33 · the one where half the array is always sorted

Now put the two ideas together: the array is rotated like the last one, but this time I'm back to looking for an actual target, still in O(log n). The key observation is quietly beautiful. No matter where the rotation happened, when you split at mid, at least one of the two halves is fully sorted. So at each step I figure out which half is the clean, sorted one, check whether the target falls inside its tidy range, and from that alone I know which half to drop.

class Solution:
    def search(self, nums: List[int], target: int) -> int:
        start, end = 0, len(nums) - 1
        while start <= end:
            mid = (start + end) // 2
            if nums[mid] == target:
                return mid
            if nums[mid] >= nums[start]:          # left half (start..mid) is sorted
                if target > nums[mid] or target < nums[start]:
                    start = mid + 1               # target is outside it, go right
                else:
                    end = mid - 1
            else:                                 # right half (mid..end) is sorted
                if target < nums[mid] or target > nums[end]:
                    end = mid - 1                 # target is outside it, go left
                else:
                    start = mid + 1
        return -1
Time O(log n)Space O(1)

The >= in nums[mid] >= nums[start] is load-bearing, not a style choice. When the window shrinks to one element, start == mid, and I want that lonely element to count as a sorted left half so the logic still has a branch to take. This is the pattern at full strength: I never ask "is the whole array sorted." I only ever ask about the half I can prove is sorted, decide the target's fate against that neat half, and throw the rest away.

The pattern, in one sentence

Binary search is only secondarily about finding a value; it's about discarding half the search space with a provable reason each step. Make it a boundary finder by recording a match and continuing toward the edge. Point it at structure (a minimum, a pivot) instead of a target when there's no target to hand. On a rotated array, lean on the half you can prove is sorted. And guarantee every branch shrinks the window, or the loop never ends.

Why I'm writing this one down

For five days the recurring lesson was reuse: don't redo work you've already done. Binary search is the harsher sibling of that idea. It's not reuse, it's refusal: don't even look at work you can prove is pointless. Halving the array feels like the trick, but halving is the easy part. The real work, every single time, was the sentence justifying why the discarded half was safe to discard, and the bug that cost me was the one case where my justification quietly didn't cover the window anymore. Day 2 taught me to prove which pointer to move. Today was the same proof, with higher stakes, because here a wrong proof doesn't just miss the answer, it can spin forever.
