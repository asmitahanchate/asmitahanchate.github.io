Arrays & Hashing: making brute force disappear

Asmita Hanchate· Nov 17, 2026· 6 min read· Arrays & Hashing

I'm re-walking the NeetCode 150 for interview practice, and I decided to write as I go, because I only really trust that I understand something once I can explain it without the solution open in another tab. This is day one. The whole category is called Arrays & Hashing, and after four problems the thing they share is almost embarrassingly simple.

Brute force, on an array, nearly always means the same thing: compare everything against everything else. Two nested loops, O(n²). It works, it passes the small test cases, and it falls over the moment the input gets real.

The hash table is the tool that makes that second loop disappear. A set or a dict gives you O(1) membership and lookup, so instead of asking "is this value somewhere else in the array?" and scanning to find out, you ask "have I already seen this?", and you've kept a note that answers instantly. You trade a little memory for a lot of time. That's the whole pattern. Here's how it shows up, getting slightly cleverer each time.

01Contains Duplicate

LeetCode 217 · the pattern in its purest form

Does any value appear twice? The brute-force instinct is to compare every pair. But a set only keeps unique values, so if turning the list into a set makes it shorter, something collapsed, which means something repeated.

class Solution:
    def hasDuplicate(self, nums: List[int]) -> bool:
        return len(nums) != len(set(nums))
Time O(n)Space O(n)

One line, and the nested loop is gone. The set does the remembering for me.

02Valid Anagram

LeetCode 242 · from membership to counting

Two strings are anagrams when every character shows up the same number of times in both. So I don't need to sort or compare positions. I just need two tallies. Python's Counter is a dict that counts for you, and two Counters are equal only when every key and count matches.

from collections import Counter

class Solution:
    def isAnagram(self, s: str, t: str) -> bool:
        return Counter(s) == Counter(t)
Time O(n + m)Space O(k) distinct chars

The jump from problem 1 to problem 2 is small but worth naming: a set remembers whether it saw something; a dict remembers how much. Once you can store a value per key, counting is free.

03Group Anagrams

LeetCode 49 · the key doesn't have to be the thing itself

This is where it got interesting for me. Group all the words that are anagrams of each other. The unlock: every anagram, when you sort its letters, produces the same string. So "eat", "tea", and "ate" all become "aet". Use that sorted string as a dictionary key, and each word drops itself into the right bucket on the way past.

class Solution:
    def groupAnagrams(self, strs: List[str]) -> List[List[str]]:
        master = {}
        for s in strs:
            key = ''.join(sorted(s))   # anagrams share a sorted key
            if key not in master:
                master[key] = []
            master[key].append(s)
        return list(master.values())
Time O(n · k log k)Space O(n · k)

The lesson that carried forward: a hash key can be something you compute, not just the raw value. The moment you can turn "these things are related" into "these things produce the same key," grouping becomes a single pass.

04Two Sum

LeetCode 1 · remember as you go

The classic. Find two numbers that add to target and return their indices. Brute force checks every pair, O(n²) again. The hash-map version flips the question around: as I walk the array, for each number I ask whether the complement (target - num) is something I've already passed. If it is, I'm done. If not, I jot down where this number lives and keep going.

class Solution:
    def twoSum(self, nums: List[int], target: int) -> List[int]:
        seen = {}                          # value maps to index
        for idx, num in enumerate(nums):
            if target - num in seen:        # have I already passed its partner?
                return [seen[target - num], idx]
            seen[num] = idx                # no, remember this one for later
Time O(n)Space O(n)

What I like about Two Sum is that the map isn't a lookup table I build first and query second. I build and query it in the same pass. Each number only ever needs to look backward at what came before, and the dict makes "look backward" cost nothing.

The pattern, in one sentence

When a brute-force solution is "for each element, scan the rest of the array," reach for a hash table and ask instead: what would I need to have remembered for this element's answer to be a single lookup? Membership wants a set. Counts want a dict. Grouping wants a dict keyed by something you compute. Pairing wants a dict you fill as you walk.

Why I'm writing these down

I've solved most of these before. Re-solving them isn't the point. Noticing the shared shape is. Four different problems, one move: stop re-reading the array, start remembering it. That reframing is what actually transfers to the next unfamiliar problem, and to real systems, where "don't recompute what you can cache" is the same idea wearing a bigger coat.
